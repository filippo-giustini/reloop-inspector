# Evaluation Protocol

## Evaluation objective

The evaluation separates **workflow correctness** from **inspection accuracy**. The current repository provides verified evidence for orchestration, safeguards, provenance, export, and runtime behavior. It does not claim production accuracy on real refurbished devices.

## Current verified evidence

| Question | Method | Current evidence |
|---|---|---|
| Does OpenCV execute? | Health call and worker result | Runtime reports OpenCV 5.0.0 |
| Can poor evidence change the next action? | Blurred front fixture | `FOCUS_TOO_LOW` requests a corrected front view |
| Is the correction verified? | Compare rejected and corrected metrics | Focus improves and passes before admission |
| Is pose view-specific? | Left/right/back fixtures | Each view must pass its own perspective rule |
| Can all views be composed? | Four-view integration test | Completion occurs only after four accepted views |
| Is the decision human-controlled? | Review unit and browser tests | Confirm, correct, defer; rationale required where appropriate |
| Is the export complete and privacy-safe? | Browser ZIP and unit test | Audit, manifest, four overlays; no source data URLs |
| Does it fit the managed runtime? | Worker and process-tree profiling | Measured headroom for isolated requests |

## Reproducible reference run

Select **Run reproducible demo**. The browser generates clearly labelled synthetic fixtures and submits them through the same public endpoint as user uploads. Only this declared synthetic path persists sources, overlays, session state, decisions and audit events in managed storage and database records; manual uploads remain browser-only. The expected sequence is one focus rejection, one verified correction, three additional accepted views, human review, and ZIP export.

Synthetic fixtures may be used to test deterministic orchestration. They must not be used to estimate precision, recall, defect prevalence, customer impact, or commercial grading accuracy.

## Real-device validation plan

A future validation set should contain consented images grouped by physical device, with front, left-oblique, right-oblique, and back captures under documented lighting conditions. Splits must occur by device rather than by image to prevent leakage.

Two independent trained reviewers should annotate capture usability, dominant failure reason, requested pose, and visible cosmetic marks. Disagreements should be adjudicated before calculating model metrics.

| Metric | Definition |
|---|---|
| Gate agreement | Share of frames where system accept/reject matches adjudicated capture usability |
| Reason-code agreement | Macro F1 across focus, exposure, glare, coverage, pose, and no-device causes |
| Corrective verification precision | Share of accepted corrective frames judged to satisfy the requested change |
| View-completion integrity | Share of completed sessions with all four independently verified views |
| Human override rate | Share of proposals corrected or deferred by reviewers |
| Processing latency | Median and 95th-percentile end-to-end time per image |

No target threshold should be represented as achieved until the real-device study is completed. Failure analysis should be stratified by background contrast, device colour, case presence, lighting, camera resolution, and occlusion.

## Reproducibility files

Raw runtime measurements are stored in `runtime_profile.tsv` and `managed_path_profile.tsv`. Computed summaries are stored alongside them as JSON. Synthetic fixtures are generated by `python/make_test_captures.py`; no customer images are included in the repository.
